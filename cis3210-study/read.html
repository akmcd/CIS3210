1. Foundations and layering

Week 0: Introduction to Networking · Kurose & Ross 1.1, 1.5

Networks are complex, so we split communication into layers of protocols; each layer wraps the data from the layer above in its own header.

  • Why networking matters:
    • Since the 1970s it went from a research topic to essential infrastructure for business, education and government.
    • It created telecommuting, new industries and demand for people who design and manage networks.
    • More connected users and services bring more value (reach, network effects) and more fragility (dependency, attack surface, congestion, shared failure points).
  • Why networking seems complex:
    • Many technologies, combined in many ways, by many companies.
    • No single theory; standards from different bodies can be incompatible; models are too simple or too complex; change is fast.
    • Terminology is inconsistent: researchers, marketers and product names reuse and overlap terms.
  • The five key aspects:
    • Network applications: how software communicates using sockets and APIs.
    • Data communications: signals, media, encoding, bandwidth, errors.
    • Packet switching: LANs, WANs, frames, MAC, Ethernet, Wi-Fi.
    • TCP/IP internetworking: addressing, routing, TCP, UDP.
    • Cross-cutting topics: performance, security, management, IoT.
  • Switching:
    • Circuit switching: set up a dedicated end-to-end connection, then transmit (telephone, telegraph).
    • Packet switching: no dedicated circuit; data is split into packets, each carrying a destination address, sent store-and-forward over shared resources.
    • Packet networks must decide addressing, address discovery, packet sizing and framing, sharing a medium, radio links, and speed/range/cost trade-offs.
  • Public vs private:
    • Public network: available by subscription through a provider. "Public" means availability, not that data is visible.
    • Private network: controlled by one organization with restricted access, possibly using leased provider links.
  • Protocols:
    • Protocol: the agreed rules for data representation, how communication begins and proceeds, message formats, and handling errors and unexpected events.
    • Interoperability: both sides follow the same rules, whatever hardware or OS they run.
    • Protocol suite (family): a set of protocols, each handling one function, that together cover all of communication. TCP/IP is the Internet's suite.
  • Why layering:
    • A layered reference model gives a complex system clear structure.
    • Modularization: a change inside one layer is transparent to the others (change the airport's gate procedure, not the whole trip).
    • Airline analogy: ticketing, baggage, gates, runway and routing each happen at both ends, like peer layers.

  • Encapsulation:
    • Each layer adds its header on the way down and the peer layer removes it on the way up (Matryoshka dolls).
    • A link-layer switch processes up to the link layer; a router processes up to the network layer. Ordinary forwarding doesn't need Ht (middleboxes such as firewalls and NATs do look at it).
    • A message split into three segments needs three datagrams and three frames on each link: headers multiply.

2. Internetworking and Internet structure

Week 1: Internetworking · Kurose & Ross 1.1–1.2

No one technology fits every need, so routers and the TCP/IP protocols join different networks into one "virtual" network.

  • Why many technologies:
    • LAN (local area network): optimized for high speed over short distances, e.g. Ethernet within a site.
    • WAN (wide area network): optimized for long distances, e.g. leased data circuits between cities.
    • Large organizations pick the best technology for each job, so they end up with several.
    • Replacing both with one technology can make things worse: it may not be optimized for either environment.
  • Universal service:
    • Universal service: any computer can reach any other, like any phone can call any phone.
    • The 1970s problem: each network was an island, so users switched computers to reach a different network.
    • You can't just wire or bridge different technologies together: each has its own frame format and addressing.
    • Universal service needs interoperability, not identical physical networks.
  • Internetworking:
    • Internetworking: hardware (routers) interconnects the networks and software (protocols) makes communication across them work. The result is an internet.
    • Router: dedicated hardware with a processor, memory and an interface per network. It can join two LANs, a LAN and a WAN, or two WANs.
    • Routers carry a common internetwork packet and re-encapsulate it in each link's native frame, so the networks never exchange native frames.
    • Several routers are used for load balancing and redundancy (no single point of failure); protocol software reroutes around failures.
    • Topology depends on bandwidth, expected traffic, reliability needs, cost and router performance.
  • Intranet vs Internet:
    • Intranet: owned by a private organization, for its employees.
    • Internet (capital I): the global Internet and its protocols.
    • The line is blurred: same equipment and protocols, and intranets connect to the Internet through gateways.
  • The virtual network:
    • Internet software hides physical connections, physical addresses and routing information.
    • Users and applications see one seamless network, so an internet is called a virtual network.
  • Nuts and bolts:
    • Hosts (end systems): billions of devices at the edge running applications, both clients and servers.
    • Packet switches: routers (connect networks) and switches (connect devices within a LAN).
    • Links: fibre, copper, radio, satellite, with a transmission rate (bandwidth) in bits/s.
    • The Internet is a network of networks built from interconnected ISPs. RFCs define the standards; the IETF develops many of them.
    • Services view: the Internet gives apps a programming interface ("hooks"), with delivery options like a postal service.
  • Edge, access, core:
    • Network edge: hosts, often servers in data centres.
    • Access network: links an end system to its first (edge) router: residential, institutional or mobile.
    • Network core: the mesh of interconnected routers and links.

  • Sending packets:
    • A host splits a message into packets of L bits and sends them at rate R (link capacity, bandwidth).
    • transmission delay = L / R
    • Example: 1,500 bytes = 12,000 bits at 100 Mbps → 12,000 / 10⁸ = 120 μs. Two packets back to back take 2L/R.
  • The four delays at each hop (textbook 1.4; the slides only use L/R and RTT):
    • Processing: examining the header and choosing the output link. Usually microseconds.
    • Queuing: waiting behind other packets for the link. Varies with traffic.
    • Transmission: pushing all the bits onto the link, L/R. Depends on packet size and link rate.
    • Propagation: a bit travelling the length of the link, d/s (distance over signal speed). Depends on distance, not packet size.
    • RTT is the round trip of a small packet, so it is mostly propagation, queuing and processing.
  • Physical media:
    • Guided: signals travel through solid media. Unguided: signals travel freely through space (radio).
    • Twisted pair: two insulated copper wires; Cat 5e: 100 Mbps/1 Gbps Ethernet, Cat 6: 10 Gbps.
    • Coax: two concentric conductors; broadband, many frequency channels.
    • Fibre: light pulses in glass; tens to hundreds of Gbps, low error rate, repeaters far apart, immune to electromagnetic noise.
    • Radio: shared, usually half-duplex; affected by reflection, obstruction, interference and noise. Wi-Fi (tens of metres), 4G/5G (kilometres), Bluetooth, terrestrial microwave, satellite.
    • GEO satellites add much more delay than low-Earth-orbit systems like Starlink.

3. Network applications

Application Layer: HTTP (first half) · Kurose & Ross 2.1

Applications are programs at the edge that exchange messages through sockets; they choose a transport protocol based on the services they need.

  • Where applications live:
    • Programs on end hosts exchange messages; you never program routers or switches.
    • Core devices only forward packets, so an app can be updated worldwide without touching any router, as long as it uses the same transport and network services.
  • Architectures:
    • Client-server: an always-on server with a fixed, well-known IP, often in a data centre. Clients initiate contact, may be online occasionally with dynamic IPs, and never talk to each other directly.
    • Peer-to-peer (P2P): no always-on server; peers both request and provide. Self-scaling (new peers add capacity and demand) and cheaper, but peers come and go, IPs change and management is harder. Example: BitTorrent.
  • Processes and sockets:
    • Programs run as processes. On one host they talk through the OS; across hosts they exchange messages over the network.
    • Client process: initiates contact. Server process: waits to be contacted. P2P apps have both.
    • Socket: the door between a process and the network (process = house). The developer controls the application side; the OS controls transport and below.
    • Every exchange involves two sockets, one on each host.
  • Addressing a process:
    • The host interface has a 32-bit IPv4 or 128-bit IPv6 address, but one host runs many processes, so the IP address alone isn't enough.
    • IP address = which host; port number = which process (socket).
    • Well-known ports: HTTP 80, SMTP 25.
  • What an application may need from transport:
    • Reliable delivery: loss-intolerant apps (file transfer, web transactions) vs loss-tolerant apps (real-time media).
    • Timing: Internet calls and games need low end-to-end delay.
    • Throughput: minimum-rate (bandwidth-sensitive) apps vs elastic apps that use whatever is available (email, file transfer).
    • Security: encryption, integrity, authentication.
  • Application-layer protocol:
    • Defines message types, their syntax, the meaning of fields, and the rules for when and how to send and respond.
    • Open protocols are in RFCs (HTTP); proprietary ones aren't (Zoom). A protocol is only one piece of an application.

  • Why an app might choose UDP:
    • No connection-setup delay; finer control over exactly when data goes out; no connection state on the server; smaller header.
    • Any reliability it needs must be built into the application (as QUIC does).
  • TLS is not a third transport protocol: it is an enhancement of TCP implemented in the application layer, providing encryption, integrity and endpoint authentication.

4. HTTP

Application Layer: HTTP · Kurose & Ross 2.2

HTTP is a stateless request-response protocol over TCP; most of its evolution is about cutting round trips and head-of-line blocking.

  • Basics:
    • The Web's application-layer protocol, client-server: the browser requests objects, the server returns them.
    • HTTP/1.1 and HTTP/2 run over TCP, on port 80 (HTTP) or 443 (HTTPS).
    • Stateless: the server isn't required to remember anything about past requests.
  • Connections:
    • RTT (round-trip time): a small packet's trip client → server → client, including propagation, queuing and processing delay.
    • Non-persistent: one TCP connection per object. Each object costs 2 RTT + transmission time: 1 RTT for the first two handshake steps, 1 RTT for the request (sent with the third handshake segment) and the response.
    • Non-persistent also costs extra setup and teardown and more TCP state and buffers on both sides.
    • Persistent (HTTP/1.1, HTTP/2): the server leaves the connection open; the whole page, and even other pages on the same server, reuse it. It closes after an idle timeout.
    • Pipelining (HTTP/1.1): send requests back to back without waiting for each response.
  • Worked counts for a base page + 10 images (ignore transmission times):
    • Non-persistent, one at a time: 11 × 2 = 22 RTT.
    • Persistent, no pipelining: 1 setup + 11 request/responses = 12 RTT. Persistence saves the 10 extra setup RTTs, not the per-object exchange.
    • Persistent with pipelining: 1 setup + 1 base + 1 for all images = about 3 RTT.

  • Request messages (ASCII):
    • GET: fetch; parameters may go in the URL (animalsearch?animal=monkey&food=banana). Body empty.
    • POST: send form or other data in the body for the server to process.
    • HEAD: same headers as GET, no body; useful for metadata and debugging.
    • PUT: send content to a URL; creates the resource or completely replaces it. DELETE: remove.
    • Host (required): the target host, needed by proxies and virtual hosting. Connection: close: don't keep the connection. User-Agent: client type. Accept-Language: content negotiation.
  • Response messages:
    • Status line (version, code, phrase, e.g. HTTP/1.1 200 OK) → header lines → blank line → entity body (the object).
    • Date: when this response was generated. Last-Modified: when the object last changed. Server, Content-Length (bytes), Content-Type; Cache-Control, Expires and ETag support caching.

  • HTTP/2:
    • HTTP/1.1 problem: responses follow request order, so small objects wait behind a large one (head-of-line, HOL, blocking), and any TCP loss delays every object.
    • HTTP/2 keeps methods, status codes and most headers, but splits objects into frames and interleaves (multiplexes) them over one connection, with priorities. It originally introduced server push.
    • Priority only changes which ready frames go first. Once TCP bytes are missing, every stream waits for in-order recovery.
  • HTTP/3 and QUIC:
    • HTTP/3 runs over QUIC (Quick UDP Internet Connections), carried in UDP, with TLS 1.3 built in.
    • Independent streams with per-stream loss recovery: missing data blocks only its own stream. Congestion control is still connection-wide.
    • Per the lecture, the Internet still has two transport protocols: QUIC is an application-layer sublayer that uses UDP. Its loss and congestion control closely mirror TCP's.
    • Setup: TCP + TLS need two serial handshakes; QUIC sets up reliability, congestion and crypto state in one 1-RTT handshake.
    • 0-RTT resumption: a returning client uses a cached TLS session ticket to send encrypted data immediately.

5. DNS

Application Layer: Email and DNS · Kurose & Ross 2.4

DNS is a distributed, hierarchical database plus an application-layer protocol (UDP port 53) that turns names into addresses, with caching doing most of the work.

  • What DNS is:
    • Hosts have a hostname (human-friendly, e.g. cs.umass.edu) and an IP address (used for routing).
    • DNS: a distributed, hierarchical database of name servers, plus an application-layer protocol (over UDP, port 53) for querying it.
    • A core Internet service implemented at the application layer: it runs on end systems as clients and servers, and uses a transport protocol. Complexity stays at the edge.
  • How a browser uses it:
    • Extract the hostname from the URL → the DNS client queries a DNS server → the reply gives the IP → the browser opens TCP to IP + port 80.
    • This adds delay; caching in nearby servers reduces both latency and traffic.
  • Services:
    • Hostname → IP translation.
    • Host aliasing: simple alias → canonical hostname.
    • Mail server aliasing: an easy domain (yahoo.com) → the mail server's canonical name, via MX records.
    • Load distribution: one name maps to several IPs; DNS rotates their order in each reply, and clients usually use the first. No HTTP inspection needed.
  • Why not centralized:
    • Single point of failure; enormous query volume (Comcast: 600 billion queries/day, Akamai: 2.2 trillion); high latency for distant users; impossible to maintain at scale.
  • The hierarchy:
    • Root servers: about 2,000 instances that are copies of 13 root servers, run by several organizations under IANA coordination. They give the addresses of TLD servers.
    • TLD servers: one (or a cluster) per top-level domain: .com (Verisign), .edu (Educause), .org, .ca, .uk… They give the addresses of authoritative servers.
    • Authoritative servers: hold an organization's own records.
    • Local DNS server: not a level of the hierarchy, but central. Provided by the ISP (via DHCP) or public (Google DNS); close to the host; acts as a proxy that resolves and caches on the host's behalf. Find yours with scutil --dns (macOS) or ipconfig /all (Windows).
  • Resolution:
    • Iterative query: the contacted server replies "I don't know, ask this server."
    • Recursive query: the contacted server does the work itself, which puts heavy load on the upper levels.
    • In practice: host → local server is recursive; local server → root, TLD and authoritative is iterative.
    • Uncached lookup: 8 messages (4 queries + 4 replies). An extra intermediate server makes it 10.
  • Caching:
    • Any server that receives a reply can cache the mapping and answer later queries itself, even though it isn't authoritative.
    • Entries expire after their TTL (often about two days).
    • Local servers also cache TLD addresses, so root servers are skipped for all but a small fraction of queries.
  • Resource records, the 4-tuple (Name, Value, Type, TTL):
    • A: hostname → IP. (web.example.com, 192.0.2.10, A, 3600)
    • NS: domain → hostname of its authoritative DNS server. (example.com, ns1.example.com, NS, 86400)
    • CNAME: alias → canonical hostname. (www.example.com, web.example.com, CNAME, 3600)
    • MX: domain → canonical name of its mail server. (example.com, mail.example.com, MX, 3600)
  • Messages (query and reply share one format):
    • Header: 16-bit identification (the reply reuses the query's number), flags (query/reply, recursion desired, recursion available, reply is authoritative), and counts for each section.
    • Question: the name and the query type (A, MX…). Answer: RRs for the name, possibly several IPs. Authority: other authoritative servers. Additional: helpful extras, such as the mail server's IP in an MX reply.

6. Email and SMTP

Application Layer: Email and DNS · Kurose & Ross 2.3

SMTP pushes mail over TCP from the sender's mail server directly to the receiver's; reading mail uses other protocols.

  • Three components:
    • User agents ("mail readers"): compose, edit and read mail. Outlook, the iPhone mail app.
    • Mail servers: hold each user's mailbox (incoming) and an outgoing message queue.
    • SMTP: the protocol between mail servers.
  • SMTP:
    • Uses TCP, port 25, for reliable transfer, directly from the sending server to the receiving server.
    • The sending server is the SMTP client because it initiates the connection; client and server are roles in one connection, so one server can be both at once on different connections.
    • Three phases: handshaking (greeting), transfer of messages, closure.
    • Command/response like HTTP: ASCII commands; replies are a status code and phrase.
  • Alice → Bob in six steps:
    • 1. Alice's user agent composes a message to bob@someschool.edu.
    • 2. It goes to Alice's mail server and into the outgoing queue.
    • 3. The SMTP client on Alice's server opens a TCP connection to Bob's server.
    • 4. After handshaking, the message is transferred.
    • 5. Bob's server stores it in Bob's mailbox.
    • 6. Bob reads it with his user agent.

  • Message format:
    • Header lines (To:, From:, Subject:) → a blank line → the body (ASCII only).
    • These header lines are part of the message, separate from SMTP's MAIL FROM and RCPT TO commands.
  • Where mail lives and how it's read:
    • Bob's mailbox is on an always-on shared server; a phone or PC can't be online all the time.
    • Relaying through Alice's server means it can retry if Bob's server is temporarily down.
    • Alice's user agent reaches her server with SMTP (or HTTP for webmail).
    • Bob reads with HTTP (webmail, phone apps like Gmail) or IMAP (desktop clients like Outlook); both let him organize, delete and mark messages.
    • SMTP is strictly a push protocol, never used by Bob to retrieve mail.

7. Socket programming

October 6 lecture · Kurose & Ross 2.6 in the 9th edition (the online knowledge checks number it 2.7) · no separate slide deck was posted

The developer writes the client and server, picks TCP or UDP when creating each socket, and the OS handles everything below the socket.

  • Two kinds of applications:
    • Open: follows a published standard (an RFC), so independently written clients and servers interoperate (Chrome + Apache). By convention its server uses the standard's well-known port (HTTP 80), so clients know where to connect; this is the textbook's guidance, not a technical requirement.
    • Proprietary: one team writes both sides with an unpublished protocol. It should avoid well-known ports so it doesn't clash with standard services (the textbook uses 12000).
  • The developer's job:
    • Write the client and server programs, and define the application's messages and rules.
    • Choose TCP or UDP when creating the socket: one of the first decisions.
    • Little control below the socket: the OS attaches the source address, and TCP does handshakes, checksums and retransmission.
  • UDP sockets:
    • socket(AF_INET, SOCK_DGRAM): AF_INET = IPv4, SOCK_DGRAM = UDP.
    • sendto(data, (serverName, serverPort)) attaches the destination to every message. A hostname triggers a DNS lookup automatically.
    • The client doesn't bind(); the OS assigns an unused port. The server bind()s the known port.
    • recvfrom(2048) returns the data and the sender's address: the return address for the reply.
    • One server socket serves every client, forever, in a while True loop.
# UDPClient.py
from socket import *
serverName = 'hostname'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(),
                    (serverName, serverPort))
modifiedMessage, serverAddress = \
    clientSocket.recvfrom(2048)
print(modifiedMessage.decode())
clientSocket.close()
# UDPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))
print("The server is ready to receive")
while True:
    message, clientAddress = \
        serverSocket.recvfrom(2048)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(),
                        clientAddress)
  • TCP sockets:
    • SOCK_STREAM = TCP. The client connect()s first; the three-way handshake happens inside the transport layer, invisible to the program.
    • After connecting, send() just drops bytes into the connection: no address attached.
    • The server's serverSocket is the welcoming (listening) socket; listen(1) sets the maximum number of queued connections.
    • accept() creates a new connectionSocket dedicated to that client. Closing it leaves the welcoming socket open for the next client.
    • The server must already be running (and listening) before the client sends.
# TCPClient.py
from socket import *
serverName = 'servername'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, serverPort))
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())
modifiedSentence = clientSocket.recv(1024)
print('From Server: ', modifiedSentence.decode())
clientSocket.close()
# TCPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
print('The server is ready to receive')
while True:
    connectionSocket, addr = serverSocket.accept()
    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())
    connectionSocket.close()
  • Socket counting (from the transport lecture):
    • A server with one listening socket and two open connections has three sockets.
    • A client talking to two TCP servers needs two connections and two sockets, and no listening socket.
    • One server process can manage many connection sockets (e.g. with threads); it doesn't need a process per connection.
  • QUIC (textbook): HTTP/3 code talks to a QUIC API, not the UDP socket API; QUIC creates a stream per message and handles encryption, framing and multiplexing.

8. Transport layer: multiplexing and demultiplexing

October 8: Transport Layer · Kurose & Ross 3.1–3.2

The network layer gets data to the right host; the transport layer gets it to the right process, using port numbers in its header.

  • What transport does:
    • Logical communication between processes: they act as if directly connected.
    • Runs only in end systems. Routers forward using network-layer fields and don't need transport headers (the slides' simplification; middleboxes like firewalls and NATs do inspect ports).
    • Sender: split messages into chunks if needed, add a transport header (making a segment), hand it to the network layer.
    • Receiver: get the segment from the network layer, process its header, deliver the data to the application.
    • Terminology: segment for both TCP and UDP; datagram is reserved for network-layer packets (the RFCs sometimes call a UDP packet a datagram).
  • Transport vs network:
    • Transport: process to process. Network: host to host.
    • Household analogy: kids = processes, houses = hosts, letters = messages, the postal service = network layer, Ann and Bill (who collect and hand out mail inside each house) = transport.
    • Substitute cousins Susan and Harvey, who lose letters, are a different transport protocol with a different service model.
  • Capabilities and limits:
    • Transport can't guarantee delay or bandwidth if the network layer can't.
    • It can add reliable delivery over an unreliable network (handling loss, corruption, duplication) and security (encryption).
    • IP: best-effort host-to-host delivery, no guarantee of delivery, order or integrity: "unreliable." Every host has at least one IP address.
    • Both UDP and TCP extend IP to process-to-process delivery and add error checking.
    • UDP adds nothing else. TCP adds reliable in-order delivery (sequence numbers, ACKs, flow control, timers) and congestion control. TCP traffic is regulated; UDP traffic is not.
    • The two apps must use compatible protocols: a TCP client can't connect to a UDP-only server, even though IP can reach the host.
  • Multiplexing and demultiplexing:
    • Multiplexing (sender): gather data from many sockets, add headers with port numbers, pass segments down.
    • Demultiplexing (receiver): use header fields to deliver each segment's data to the correct socket.
    • Needed in every network, and wherever one protocol serves several protocols above it.
    • Ports: 16 bits, 0–65,535; 0–1023 are well-known (HTTP 80, FTP 21); new applications must be assigned a valid port.
    • UDP sockets: without bind(), the OS assigns a temporary port on the first send; servers bind ports their clients know (DNS: UDP 53).

9. UDP

October 15: User Datagram Protocol · Kurose & Ross 3.3 · Comer Ch. 24

UDP is a thin layer over IP: port-based delivery between applications, an error check, and nothing more.

  • Characteristics:
    • End-to-end: distinguishes multiple applications on one computer (by port), independent of OS process IDs.
    • Connectionless: no setup before sending, no connection state, no control messages; send any time and wait as long as you like between messages. Extremely low overhead.
    • Message-oriented: each send becomes exactly one UDP datagram; UDP never splits or combines messages, so boundaries are preserved.
    • Best-effort: the same delivery semantics as IP.
    • Arbitrary interaction: send to many, receive from many, or talk to exactly one application.
    • "Simpler than TCP" is not enough reason to choose it: the service must fit the app, or the app must add what's missing.
  • Message size:
    • Each message must fit in one IP datagram; if it's too big the send fails and the app must split it.
    • Tiny messages have high header overhead relative to data.
    • Messages over the path MTU may be fragmented by IPv4 (if allowed) and reassembled by IP at the destination, so the app still gets one message. Fragmentation reduces efficiency.
    • Best: large messages, with the whole IP datagram, headers included, within the path MTU.
    • If the app splits a message into three, they travel as three datagrams; the receiving app must recombine them and handle loss and reordering.
  • Sender and receiver actions:
    • Sender: take the app message, fill in header fields, create the segment, pass it to IP.
    • Receiver: get the segment from IP, check the checksum, extract the message, demultiplex it up through the socket.
    • To send, the app supplies destination IP + port. The port goes in the UDP header; the IP address is passed to IP for the IP header.
    • Reply ports swap: request src 50501 / dst 50502 → reply src 50502 / dst 50501.

  • The checksum:
    • Sender: treat the segment as 16-bit words, add them with one's complement arithmetic (any carry out of the top bit wraps around and is added back in), then flip every bit.
    • Receiver: add all words including the checksum. All 1s = no error detected; any 0 = error.
    • Why, when links check errors too: not every link does, and bits can be corrupted in router memory. Only an end-to-end check covers the whole path.
    • Limits: detects only, no correction or recovery; UDP silently discards a bad segment. Weak: compensating bit flips can leave the sum unchanged.

10. Reliable data transfer: rdt1.0 to rdt3.0

October 20: Reliable Data Transfer · Kurose & Ross 3.4.1–3.4.2

Build a reliable channel on an unreliable one by adding, one problem at a time: checksums, feedback, sequence numbers, and timers.

  • The problem:
    • Present at the transport, link and application layers; TCP is the prime example.
    • Service abstraction: the upper layer sees a channel with no corruption, no loss, in-order delivery. That says nothing about the network itself being reliable.
    • Data flows one way, but control messages flow both ways.
    • Sender and receiver can't see each other's state unless it's explicitly communicated: silence is ambiguous.
    • The kind of channel errors (loss, corruption, reordering) shapes how complex the protocol must be.
  • Interfaces:
    • rdt_send(): called from above at the sender with data to deliver.
    • udt_send(): called by rdt to send a packet over the unreliable channel.
    • rdt_rcv(): called when a packet arrives at the receiver side of the channel.
    • deliver_data(): called by rdt to hand data up at the receiver.
    • The goal: each rdt_send leads to exactly one deliver_data, however many udt_sends happen. That's only achievable if the channel eventually lets some packets through.
  • Finite-state machines (FSMs):
    • Separate FSMs for sender and receiver. Each transition is labelled event over actions; Λ means no event or no action.
  • rdt1.0: perfectly reliable channel.
    • Sender: make_pkt(data), udt_send. Receiver: extract, deliver_data. One state each, no feedback.
    • Even if the channel duplicated a packet, comparing data values can't detect it: the app may legitimately send the same data twice. There is no packet identity.
  • rdt2.0: bits may be corrupted (no loss, no reordering).
    • Human analogy, dictation: "OK" = ACK, "repeat" = NAK. These are ARQ (Automatic Repeat reQuest) protocols.
    • Needs error detection (checksum), receiver feedback (ACK/NAK), and retransmission.
    • Sender has 2 states: wait for data, then wait for ACK/NAK (retransmit on NAK). No new data until a valid ACK: stop-and-wait.
    • Receiver has 1 state: ACK if good, NAK if corrupted.
    • Fatal flaw: ACK/NAK packets can be corrupted too, and then the sender can't tell what happened.
    • Fixes considered: ask "what did you say?" (can loop forever), use an error-correcting code (no help with loss), or retransmit the data (creates duplicates the receiver can't recognize).
  • rdt2.1: handles corrupted ACK/NAK.
    • Add a sequence number to data packets. For stop-and-wait, 1 bit (0/1) is enough.
    • ACK/NAKs need no number: they always refer to the last packet sent.
    • Garbled feedback → retransmit with the same number. Relabelling it would make old data look new and cause duplicate delivery.
    • Receiver: corrupted → NAK; duplicate (old number) → ACK without delivering again.
    • FSMs double: 4 sender states, 2 receiver states (expect 0 / expect 1), mirror images of each other.
  • rdt2.2: NAK-free.
    • The receiver ACKs the last correctly received packet, including its sequence number (ACK0 or ACK1).
    • An ACK for the previous packet (a duplicate ACK) means "the current one didn't arrive": retransmit.
    • The sender retransmits if the ACK is corrupted or carries the wrong number. Still stop-and-wait.
  • rdt3.0: the channel can also lose packets.
    • New mechanism: a countdown timer. Start it on every send (including retransmissions), stop it on the correct ACK, retransmit on timeout.
    • No reply could mean the data was lost, the ACK was lost, or either was delayed. The sender can't tell, so the action is always the same: retransmit.
    • The timeout is chosen so loss is likely, not certain; a premature timeout creates duplicates that sequence numbers already handle.
    • In "wait for ACK" states, a corrupted ACK or wrong-numbered ACK causes no action (Λ): recovery waits for the timer.
    • Receiver: same FSM as rdt2.2. With alternating 0/1 numbers it is the alternating-bit protocol.

  • Stop-and-wait performance:
    • U_sender = (L/R) / (RTT + L/R)
    • Cross-country example: L = 8,000 bits, R = 1 Gbps → L/R = 8 μs = 0.008 ms; RTT = 30 ms.
    • U = 0.008 / 30.008 ≈ 0.00027; throughput ≈ 8,000 bits / 30.008 ms ≈ 267 kbps on a 1 Gbps link.
    • The protocol, not the hardware, limits capacity. Processing and queuing delays only make it worse.

11. Pipelining: Go-Back-N and Selective Repeat

October 20: Reliable Data Transfer (second half) · Kurose & Ross 3.4.2–3.4.4

Keep many packets in flight. GBN keeps the receiver simple and resends a lot; SR resends only what's missing but needs buffering and a careful window size.

  • Pipelining:
    • Send multiple packets before waiting for ACKs: 3 packets triple the utilization.
    • U_sender = N·(L/R) / (RTT + L/R)
    • Example: 3 × 0.008 / 30.008 ≈ 0.0008. Filling the pipe needs about 30.008 / 0.008 ≈ 3,751 packets in flight.
    • Consequences: a larger sequence-number range (each unACKed packet needs a unique number), sender buffering of unACKed packets, and sometimes receiver buffering of out-of-order packets.
    • k-bit sequence numbers: range 0 to 2ᵏ − 1, with modulo 2ᵏ arithmetic.
  • Go-Back-N sender:
    • At most N unACKed packets (window size); a sliding-window protocol.
    • Regions: [0, send_base − 1] ACKed · [send_base, nextseqnum − 1] sent, not ACKed · [nextseqnum, send_base + N − 1] usable · beyond that not usable.
    • Cumulative ACK(n): everything ≤ n received; the window slides to n + 1.
    • One timer, for the oldest unACKed packet. timeout(n): resend n and every later packet in the window.
    • If the window is full when data comes from above, the data is refused (or buffered).
  • Go-Back-N receiver:
    • ACKs the highest in-order sequence number received, so duplicate ACKs are normal.
    • Tracks only rcv_base (the next expected number).
    • Out-of-order packets: discard (or buffer, a design choice) and re-ACK the last in-order packet.
    • Inefficient when windows are large or errors are frequent: one error resends many packets that already arrived.
  • Selective Repeat sender:
    • Retransmits only lost or corrupted packets, using one logical timer per packet (one hardware timer can simulate many).
    • Data from above: send if its number is in the window; otherwise buffer or refuse.
    • ACK received: mark that packet. If it was send_base, slide the window to the next unACKed packet and send any newly allowed packets.
  • Selective Repeat receiver:
    • In window [rcv_base, rcv_base + N − 1]: send a selective ACK; buffer it if new; if it equals rcv_base, deliver it and the consecutive buffered packets and slide the window.
    • In [rcv_base − N, rcv_base − 1] (already received): re-ACK it, or the sender's window may never move.
    • Otherwise: ignore.
    • Sender and receiver windows don't always line up.
  • The SR dilemma:
    • Sequence numbers 0–3, window 3. If all ACKs are lost, the sender resends old pkt0, but the receiver's window already expects a new pkt0, so it accepts old data as new.
    • The receiver can't see the sender's side; both cases look identical to it.
    • Rule: window ≤ half the sequence-number space (3 bits → 8 numbers → window ≤ 4).
